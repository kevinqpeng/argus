# 形式化验证与边界用例

先读 [共享契约](../../references/contracts.md) 和 [形式化路由](../../../decision-router/references/formal-routing.md)。由 Argus 或 prd-to-cases 调用，复用冻结角色与预算，不新增模型角色。输入为 AC、候选场景、源码或协议证据、版本和本 run 的 workspacePath。

reasoning 负责性质与边界分析，generation 生成模型和用例，bug_analysis 核查模型偏差与反例归因；按 setup 的冻结角色映射调用，不由主会话冒充缺失角色。

## 1. 确定检查范围

- 按当前宿主技能目录定位并读取 `pstack:create-formal-verification-skill`，已有模型还读 `pstack:maintain-formal-verification-skill`；TLA+ 结果通过 `pstack:statechart` 解读。按技能名定位当前安装版本，不保存插件缓存绝对路径，不复制其命令或实现。所选依赖缺失标 BLOCKED，保留未覆盖义务。
- 采用 pstack 的源码映射、故障变体、反例回放和模型漂移检查。Argus 的资产位置与授权优先：模型、配置、故障副本和 harness 全部写本 run 的 `formal/`，项目源码、依赖及项目技能只读。无需为每次验收再安装项目技能。
- 为每个检查建立稳定 checkId，绑定 acIds、scenarioIds、来源定位及哈希。写一句业务性质和违反后的损害。只选择当前授权范围，不能为了建模扩展业务要求。
- 有源码时逐个核对状态写入者、事务、锁、读写和外部调用的真实原子边界。无源码时标为需求或协议模型，记录未知实现假设，结论只针对该模型。模型与实现不一致先修正模型，不削弱已确认性质来消除失败。

## 2. 建模并核对边界

- 写 Init、按真实原子操作拆分的 Next、TypeOK、安全 INVARIANT。按适用性纳入竞争者、请求标识、重复和乱序消息、超时后成功、崩溃恢复、取消与提交交错。不能把业务的检查与写入擅自合成一个原子动作。
- 活性要求使用 PROPERTY，并记录调度与环境公平性假设，不能把“最终完成”写成某个状态的安全断言。活性检查禁用 SYMMETRY。参考 [TLC 配置](https://github.com/tlaplus/vscode-tlaplus/blob/master/resources/knowledgebase/tlc-config-files.md) 和 [对称性限制](https://dl.tlapl.us/tlatoolbox/doc/model/model-values.html)。
- 有限常量覆盖 0、1、多个主体或容量的适用边界；记录每个配置、约束、状态上限、时间和内存预算。范围缩小要保留原结果并披露，不能把截断当穷尽。合法终态使用仅在终态启用的停留动作，保持其他状态的死锁检查。
- 使用已有模型前比较源码及本地改动哈希、PRD、配置、性质与上次同步依据；漂移时按 maintain 技能重建映射，不能直接复用旧通过结论。

## 3. 检查模型并校准性质

- 基线冻结前允许在仓库外运行不接触业务目标的 TLC，作为用例设计分析。运行真实应用、API、数据库以及真实代码的故障回放仍须人工用例评审门禁。直接调用本技能同样受此限制。
- 读取当前 statechart 技能后执行其真实命令，记录解析后的技能位置、工具版本、完整命令、配置与模型哈希、退出码、原始 TLC 输出及完成状态。图用于理解，不以图是否生成或包装脚本退出 0 判断性质通过。
- 每项性质分别记录 passed、failed、error 或 blocked。只有指定有限模型完整检查、没有未检查性质、没有反例且模型映射与校准有效，才记 passed。超时、状态截断、缺依赖或未运行保持 blocked；语法和工具执行错误记 error。发现反例即 failed，即使其他性质未完成也保留该反例。
- 在隔离模型副本移除相关保护或拆开错误的原子步骤，确认每项性质能检出对应故障；标明这是模型校准。正常模型也失败时保留发现，不要求把它改成通过。真实代码变体校准仅在已批准的隔离 harness 中运行，不修改项目。无法校准则性质保持 blocked，不能宣称验证有效。

## 4. 把结果转成可执行用例

- 将每条反例写成业务操作序列，记录 action 到源码或协议的映射、初始数据、调度屏障、期望与最终副作用。安全反例记录到违规状态的路径；活性反例保留前缀和循环，有限回放不能独自证明无限活性。
- 交回 [prd-to-cases](../../../prd-to-cases/SKILL.md) 生成稳定场景与 caseId。即使未发现反例，也从已建模的边界、竞争次序和恢复路径导出适用的真实测试义务，逐项记录已有用例或缺口。模型状态数与路径条数不作为场景分母。
- 正常冻结、计划门禁与人工评审后，按原 web/mobile/API 路径回放。断言业务结果、持久状态和副作用次数；不能用随机 sleep 声称控制了交错。目标无法控制交错时标 blocked 并记录无法验证的路径。
- 不能在实现中重现时先核对模型原子性、前置条件和可达性，标为模型偏差或待确认，不能直接发布已确认产品 Bug。真实重现后按 bug-reporter 分类、去重与交付。
- 冻结后发现新义务，保留原基线指标与结果，按输入变化规则新建 run、更新基线与评审材料并重新评审；不能悄悄改变已批准用例。缺陷回归仍保留原 Bug 和原用例关联。

## 5. 留存与汇总

将 `formal/results.json` 作为形式化事实来源，外层 `schemaVersion: 1`，含 runId、inputHash、路由记录引用、checks。每项检查记录 checkId、acIds、scenarioIds、caseIds、来源和同步哈希、模型与配置哈希、性质、界限与假设、命令与工具版本、各性质状态、完成证据、故障校准证据、反例引用、真实回放结果引用和未覆盖义务。无法取得的值写 unknown 或明确缺口，不伪造。

在 `manifest.gates.formalVerification` 记 status、reason 和 evidenceRef 指向 results.json。路由明确不适用为 N/A；未决路由、所选检查未完成、模型反例未解决或回放义务未满足为 BLOCKED。全部所选性质与真实回放义务有通过证据才为 PASSED。用例设计期间可以交付待评审材料，不能提前标最终门禁通过。

冻结 inputHash 时纳入形式化路由题目版本、所选模型和配置哈希、性质与界限，以及来源映射。这些输入变化时使旧缓存及审批绑定失效，按共享契约新建 run，不修改旧快照。

业务覆盖仍由 [coverage-check](../../../coverage-check/SKILL.md) 计算，仅真实 runner 发现并执行的 ui/api 用例进入业务指标。模型结果不写成业务 attempts，也不新增 formal suite。报告分别列模型界限内结论、真实回放覆盖和剩余缺口；形式化门禁 BLOCKED 时全量验收不能通过。
