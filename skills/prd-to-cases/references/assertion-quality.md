# 断言质量：写得出可观察结果，才算验过

断言是本技能的交付核心。评审表可以润色，用例骨架可以合并，但断言不准就是用例不准——一条「状态正确」等于没写。本文件约束生成 worker 和补齐轮写断言的方式，由 `generation.py` 的结构校验、`assertion_check.py` 的措辞检查、`coverage_check.py` 的量词检查共同看守。

## 1. 断言必须落到可观察对象上

每条断言回答三件事：**谁/哪个对象**、**操作后变成什么**、**凭什么肉眼或接口能确认**。三者缺一句就是弱断言。

- 可观察对象是界面元素、列表与记录条目、待办归属、申请与节点状态、提示文案、条数与字段值。
- 内部实现（状态变量名、落库字段、枚举值、请求体）不是可观察对象，写在 evidenceRef 里，不写进断言。
- 观察不到就说明证据不足，写待确认，不拿「正确」「符合预期」占位。

## 2. 四类必须成套的断言

以下场景出现时必须按模板写全，缺一套就是弱化用例：

### 2.1 路径类：列出节点清单，并明说不含谁

用于驳回后重新发起、从当前节点继续、换版重审、加签后重审。

```
DON'T  新一轮审批路径符合预期 / 按预测路径重新审批
DO     再次提交后，新一轮审批依次为 A、C、D；节点清单中没有 B
DO     提示为「调整后的审批路径不经过原驳回节点，已从流程起点重新审批」，新一轮从 A 开始
```

只写「经过/不经过」不给清单等于没给结论；反过来只给清单不说「不含谁」，评审无法判断是不是漏了一个节点。

锚点必须是**节点身份**，不能是代词。「流程起点」「原节点」「发起人」「当前节点」都指向一个具体节点，换成换版、分支变化、加签之后就不再成立；来源给了 `anchors.start` 时，断言里必须出现那个标识。

```text
DON'T  再次提交后待办出现在 A 节点            # A 是旧路径的节点，换版后可能是 A1
DON'T  重新发起后从流程起点重新审批            # 起点是哪个节点，没说
DO     再次提交后新一轮从 B0 开始，依次为 B0、B1、B2；节点清单中没有 C
```

`assertion_check.py` 对路径断言只写代词、来源 `anchors.start` 没落进断言两种情况直接阻断；给了标识但没给清单只提示。

### 2.2 记录类：条数、顺序、旧行、当前节点，四件套

用于「记录保留并继续追加」类需求。四件必须写在同一用例里，且增量断言前先有一步读取基线。

```
DON'T  原来的审批记录都保留了
DO     再次提交前，流转记录共 4 条
DO     再次提交后共 5 条，新增的是一条提交记录，排在两条旧记录之后
DO     旧的两条记录处理人、时间、意见与原值相同，没有合并或覆盖
DO     流转记录中当前节点标记落在 A
```

「记录保留」是明确的禁用措辞：它既不说是哪条记录，也不说哪个字段没变。记录有追加或保留时，`assertion_check.py` 缺条数直接阻断，缺顺序、旧行未改写、当前节点标记只提示。

四件套只留在 cases.json。评审表改成两句能扫读的话：路径写「从 A 开始，按照 A>B>C>D」；记录写成列表「-A（当前节点）」「-C驳回【驳回后重新发起】」。不把「先记下有几条」写成操作步骤，也不写「第 2 条」。

### 2.3 结构类：先断字段与按钮集合，再断行为

用于弹窗、表单、开关配置页、详情页按钮。结构断言能让「多出一个下拉框」这种偏差被抓住。

```
DON'T  弹窗展示重新审批方式选项
DO     弹窗内只有驳回意见、重新审批方式、抄送人、抄送意见四项；按钮为「取消」「确定」
DO     未选方式点确定时，弹窗不关闭，方式下方出现红字「请选择重新审批方式」
```

### 2.4 配置类：界面状态与服务端取值必须对照

凡「保存」「开关」「配置项」「发布」类需求，只断界面等于没验持久化。

```
DON'T  开关保存成功
DO     保存后提示「保存成功」，退出并重新进入该模型的「更多设置」，开关仍为开启
DO     该模型的配置详情接口返回允许驳回后继续审批为 true（suite=api）
```

同一需求里至少有一条 `suite=api` 用例承接配置读写；全部用例都是 `suite=ui` 时，`assertion_check.py` 会提示。接口返回、字段名和「读回」只写在这条用例的断言里。评审表写「重新进入后开关仍为开启」。

## 3. 禁用措辞（BLOCKED）

`assertion_check.py` 直接阻断下列写法，改写成具体对象与值：

`符合预期`、`如预期`、`功能正常`、`正常工作`、`一切正常`、`无异常`、`状态正常`、`显示正常`、`表现正常`、`正确地`、`合理性`、`相关问题`、`等等`、`若干`、`适当`、`尽量`、`视情况`、`大概`、`可能是`、`记录保留`、`数据保留`。

断言里出现单独的「或」「/」表示结论不唯一，也阻断：要么确认唯一结果，要么拆成两条用例。

## 4. 量词与副作用

- 保留来源的数量词与范围：来源只说「任一人可审批」时，不得写成「双方各自收到待办」；来源未写分配策略时写待确认（`coverage_check.py` 双向拦截，见主 Skill 第 5 节）。
- 同一业务动作产生多个副作用时，逐个断言：待办增减、记录条数、通知条数、实例状态分别写，不合并成一句「处理完成」。
- 增量断言必须同用例内先读基线（步骤里读条数或状态），再写差值。

## 5. 自检

生成分片 seal 通过、合并之后跑一次即可，不逐片跑（省掉重复检查与逐片重派）：

```
python3 <本技能>/scripts/assertion_check.py <runDir>
```

退出 2 时按报错改断言；提示项（warning）在报告里说明取舍，不改用例也能过门禁。阻断项有四类：弱措辞与或然结论、路径断言只有代词、来源 `anchors.start` 没落进断言、记录追加类不给条数；路径类义务既没 `anchors.start` 也没 `waiver` 同样阻断。检查只证明没有弱表述，不证明业务结论正确——结论对错仍需来源核对与人评审。
