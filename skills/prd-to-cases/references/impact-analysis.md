# 变更影响与测试义务

在提取 AC 和冻结场景前执行；恢复和缺陷回归也核对本轮来源。产物为本 run 的 `cases/impact-analysis.json`，结构见共享 schema 的 ImpactAnalysis。该分析只读来源，不连接业务目标执行测试或数据库核验。

## 1. 来源清单与变更对象

完整读取 PRD 的章节、表格、原型说明及适用附件。先按来源建立 sourceUnits 清单，再提取义务；逐项记录定位和处理结果，不能由已经生成的场景反推来源清单。以 PRD 描述本次需求，以冻结 main 内的源码、规则和契约追踪既有业务。每个来源保存稳定 sourceId、kind、sourceRef 和原始字节 SHA-256；网页等来源保存可复核的内容快照。确认来源适用版本及有效性。

sourceUnits 按独立规则和原表行建立，不以“入口/配置/记录”等模块摘要代替。每项保存 `sourceExcerpt` 原文及 `evidenceRef` 的章节/行/单元格；从同一冻结快照读回，核对定位和片段一致。相同规则可共享义务，但保留各来源行；标题、前置条件、预期互相矛盾时保留冲突，不按标题推定已覆盖。

冻结前从原文分段批量调用 `source_inventory`：每段提供完整 `sourceContent`、对应 sourceUnits 和 obligations，不提供仅由用例反推的摘要。检查例外、状态转换和失败分支是否进入义务；在段落边界保留关联规则上下文。回执写入现有探索材料，sourceUnit.reviewRef 指向该回执及宿主核查。no/uncertain 先找缺项并补齐或标 unknown；来源清单全部有处置才完成。原文未读或缺附件时不能因已登记项100%而宣布来源完整。

提取本次新增/修改/删除的对象、字段、操作、状态与权限边界，写 objects。对象 description 明确变更前后语义；区分“某张工单执行人”与“工单所属业务对象归属人”。从这些对象出发，沿既有业务依赖追踪 PRD 未描述的场景。

### 冻结生产稳定业务基线

在被测项目中一次解析代表线上稳定业务的 main 引用，记录仓库、引用名和完整提交 SHA。整轮从该提交对象读取文件（例如 `git show <SHA>:<path>`），将 `仓库@SHA:路径` 及行段写入 sourceRef/evidenceRef，并按原始文件字节计算来源哈希。复核和恢复也读取同一提交；main 后续移动不改变本轮基线。缺少可验证的 main 时保留 PRD 可证实的义务，相关依赖标 unknown 并列出缺口。

设计只使用 PRD 与该快照，不检索目标 PR、需求提交、共享测试分支或工作区差异。impactHash 绑定上述来源与六维分析结果。实际环境记录留在评审后的探索证据中；只有正式采纳新规则或更换设计基线时才更新设计材料并按原门禁评审。

kind 为 prd / business_rule / contract / history / code / observation。代码与观察说明实际依赖或行为，不自动证明预期正确；历史用例也需核对有效性。冲突或缺证据先登记 unknown 和待确认义务，不能挑选最容易通过的来源。

## 2. 按对象追踪影响

先按 [探索调度](impact-exploration.md) 核对复杂度和可拆分范围：简单需求单 Agent，复杂需求按冻结 reasoning 配置调度并行探索；发现新依赖时重新评估。该流程在本节六维追踪之前分工，在确认测试义务之前完成合并与边界复核。

每个对象都检查以下六个 dimension，可有多条 check；每条实际依赖单独记录，不能用一条笼统“已检查”替代依赖清单。

| dimension | 检查内容 |
|---|---|
| data | 共用实体、关联记录、字段读写者、调用者及消费者；包括未修改的模块 |
| inflight | 处理中、待审核、待结算、待回调等在途业务；0、1、多条关联记录 |
| lifecycle | 变更前后新建记录、合法/非法状态转换、终态历史记录、删除与恢复 |
| permission | 新旧责任人的查看/操作/审批权限，角色、租户及数据边界 |
| side_effect | 待办、通知、统计、搜索、缓存、SLA、任务及外部系统 |
| ordering | 重复、乱序、并发、超时后成功、部分失败、回滚及补偿 |

有源码时沿调用、读写、消息和契约追踪，包含定时任务与异步消费者。发现下一条依赖继续追踪，直到有证据说明不受影响或到达明确的已分析边界；不固定只看一层或改动文件。evidenceRef 指向代码位置、协议、快照或检索记录，reason 写清依赖路径与停止依据。缺源码时用 PRD 及其附件核对已知规则；仍无法判定的分支保留 unknown，不伪造 not_applicable。

每条 reason 写明本维度的触发操作、相关业务状态、依赖路径及可观察结果。用 `impact_evidence` 对照 change、check、dependencyEvidence 核查；六个维度复制“CRUD已覆盖”不能证明检查完成。相同来源可复用，依赖结论须逐项成立；低概率按 unknown 处理，不以文本相似度自动判业务错误。

sourceUnits 与 checks 共用以下处置字段：

- sourceIds：本条证据来源 ID；evidenceRef：精确定位；reason：影响、排除或未知原因；reviewRef：真实核查依据。
- disposition=covered：形成一项或多项 obligationIds。
- disposition=not_applicable：有证据证明不构成测试义务，obligationIds=[]。来源中的背景介绍可以如此登记；不能用于难测、未知、预算不足或未经授权的相关场景。
- disposition=unknown：规则、影响或证据未知，保留问题与候选义务；门禁阻断。
- disposition=out_of_scope：已知相关但本次授权不包含，保留关联义务和人工范围决定；全量门禁阻断，只能交付 partial。范围重新批准时另建 run/基线并保留原缺口。

需要语义判断时使用 decision-router 的 impact_relevance、obligation_equivalence、rule_support 集中题目；独立问题批量提交，沿用集中阈值。证据缺失先补证据；中间概率或失败保留 unknown。高概率不是业务批准，no 也不能自动删除依赖。

## 3. 确认测试义务与预期

obligations 每项表示一个独立业务规则，保存 obligationId、sourceIds、text、expected、acIds、reviewStatus、approvalRef。未知预期可先留空并标 needs_clarification，进入待确认清单；进入冻结基线前每项都必须 approved、预期明确并映射 AC。approvalRef 指向适用的既有权威规则或真实业务确认；仅有代码现状、模型结论或“reviewed”标签不算业务依据。复用已确认规则无需重复询问。

按受影响模块将问题交给对应负责人核对；提问附影响路径、当前行为、可选规则与差异，不要求当前产品经理独自回忆全部模块。人工用例评审仍遵循共享契约，与此处规则确认分开。

例：归属由 A 转交 B，A 还有该对象的处理中与待审核工单。分别确认保留、转交、撤销重建或阻止变更的条件；其他对象的工单、已完成记录是否保持不变。继续检查 B 无权限、两端待办、变更与完成交错、部分失败和重复消息。未确认时不把“同步转交”编成预期。

建立业务决策表：关联关系 × 状态 × 权限 × 操作顺序 → 预期及副作用。覆盖每个有效规则分支和非法转换；高影响交错走已有形式化路由。仅对证据表明独立的维度压缩组合，不用两两组合替代业务耦合分支。检查操作返回、主对象、关联对象、权限与副作用，以及明确不应变化的记录。多 AC 共用用例分别绑定有效断言。

按实际规则枚举：责任人0/1/多与部分办结、变更前/后、配置不存在/启用/停用/删除、默认/指定/失效模板、初始空态/筛选空态/请求失败；不适用项记录依据。转办、加签、节点流转和规则变更要用动作序列验证，历史分桶或伪造参数只覆盖各自的静态/接口规则。范围内缺夹具或等待成本高时保留用例及执行阻塞，不缩小设计分母。产品明确排除的规则保留原批准范围，不自动扩测。

## 4. 冻结、评审和复用

coverage 聚合输入内嵌 impactAnalysis，impactHash=coverage.digest(impactAnalysis)。currentSourceHashes 是宿主本次重新读取来源得到的 sourceId → 原始字节哈希；不能复制旧值冒充当前证据。sourceHash/currentSourceHash 保留原 PRD 指纹语义；AC 新增 sourceId，自己的 sourceHash 匹配该来源，sourceRef 指向具体规则。

生成与执行 inputHash、评审 artifactHashes 均绑定本文件；来源、义务、影响范围、规则或题集变化按输入变化新建 run，并重新评审。旧 run 缺少本分析不得自动通过或修改历史审批；在新 run 补分析后再恢复执行。

完整来源、检查、义务、处置和证据保留在 impact-analysis.json 与内部追踪 Markdown，包含 unknown、not_applicable、out_of_scope；不能只保留已生成用例。按 [评审表生成契约](review-table.md) 将需要人员决策的规则、范围及环境限制整理为白话「待确认事项」，通过内部映射关联来源。核对每项未决问题均有展示去向；规则未明时可交付待讨论材料，不能宣称生成完整或验收通过。

宿主先核对来源清单和真实依赖证据；coverage.py 再检查来源处置、六维检查、义务到 AC 的映射及有效用例。报告分别展示来源单元处置、影响检查处置、规则明确、必需场景设计和执行覆盖；前两项的 100% 只针对已登记集合，不证明未知依赖不存在。源码缺失、检索边界、剩余未知和排除项单列。

确认后的规则和实际漏测案例可在项目私有工作区复用，保留来源版本、业务对象、适用条件、批准依据及关联缺陷；本轮加载时重新验证，不把推断沉淀成规则。现有用例库仍只读，无需新增知识图谱服务。
